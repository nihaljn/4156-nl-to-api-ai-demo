# SPEC.md — SubTrack v1

This is the spec committed to the repo and handed to the agent. Every rule in it is testable, and every test in the acceptance list traces to a rule.

## 1. Overview and scope

SubTrack is a REST service that tracks subscriptions for client programs: plans, which customers are on which plan, when each subscription bills, and its status on any given day. It never moves money; clients charge through their own payment processor.

**In scope:** the five endpoints in section 5, the rules in section 4, and the acceptance tests in section 7.

**Out of scope for v1.** If a request seems to need one of these, return an error. Don't add the feature.

- Charging cards, refunds, proration, invoices
- Editing or deleting plans; upgrading or downgrading between plans
- Pausing a subscription
- Times of day and time zones other than UTC
- Pagination (the billing-dates window is capped at 92 days instead)
- Webhooks or notifications
- Data that survives a restart (the demo uses H2 in memory)

**Stack:** Java 17, Spring Boot 3, Maven wrapper (`./mvnw`), H2. Done means `./mvnw verify` passes, which runs JUnit, JaCoCo, Checkstyle and PMD.

## 2. Conventions

These apply to every endpoint. Section 5 doesn't repeat them.

| Topic | Rule |
| --- | --- |
| Client identity | Every request carries `X-Client-Key: <string>`. A missing or blank key returns `401 UNAUTHENTICATED`. Any non-blank key is accepted and identifies a client; there is no key registration in v1. |
| Isolation | A client sees only plans and subscriptions it created. Another client's ID behaves exactly like an ID that doesn't exist (`404`). |
| Content type | Request and response bodies are `application/json`. Unknown request fields are ignored. A missing or unparseable body returns `400 MALFORMED_REQUEST`. |
| Dates | Every date is an ISO calendar date (`YYYY-MM-DD`) in UTC. No field holds a time of day. |
| Today | `today = LocalDate.now(clock)`, where `clock` is a `java.time.Clock` bean set to UTC. Nothing else may read the system time. Tests replace the bean with `Clock.fixed(...)`. |
| Money | Integer cents in fields ending `Cents`. Never floating point. |
| IDs | Generated by the service: `pln_` or `sub_` followed by 10 lowercase letters or digits. Customer IDs come from the client and are stored as given. |
| Idempotency | `POST /plans` and `POST /subscriptions` accept an optional `Idempotency-Key` header (1–100 characters), scoped per client. The first request with a key is processed normally, and its status and body are stored. A repeat with the same key and the same body returns the stored status and body without writing. A repeat with the same key and a different body returns `409 IDEMPOTENCY_MISMATCH`. Two concurrent requests with the same key must not both write. |
| Errors | Every non-2xx response has the body below. `field` is present only when one input field is to blame. |

```json
{ "error": "VALIDATION_ERROR", "message": "trialDays must be between 0 and 30", "field": "trialDays" }
```

## 3. Data model

Only these fields are stored. Status, current period and next billing date are derived on every read (section 4) and never stored.

**Plan**

| Field | Type | Constraint |
| --- | --- | --- |
| `planId` | string | Generated, `pln_` + 10 characters |
| `name` | string | 1–100 characters after trimming; unique per client, ignoring case |
| `priceCents` | integer | 1 to 10,000,000 |
| `currency` | string | 3 uppercase letters, a valid `java.util.Currency` code |
| `interval` | enum | `MONTH` or `YEAR` |
| `trialDays` | integer | 0 to 30 |

**Subscription**

| Field | Type | Constraint |
| --- | --- | --- |
| `subscriptionId` | string | Generated, `sub_` + 10 characters |
| `planId` | string | An existing plan of the same client |
| `customerId` | string | 1–64 characters from `A–Z a–z 0–9 _ -` |
| `startDate` | date | On or before today |
| `firstBillingOn` | date | Set once at creation: `startDate + trialDays` (rule R1) |
| `endsOn` | date or null | Set by cancel (rule R7) |
| `cancelMode` | enum or null | `AT_PERIOD_END` or `IMMEDIATE`, the mode that set `endsOn` |
| `canceledOn` | date or null | The day the cancel request that set `endsOn` arrived |

## 4. Rules

Every rule takes a date `D`: the request's `asOf`, or today when there is none. Each rule has an ID so tests and code comments can cite it.

- **R1 — First billing date.** `firstBillingOn = startDate.plusDays(trialDays)`.
- **R2 — Billing dates.** `billing(k) = firstBillingOn.plusMonths(k)` for `MONTH`, or `.plusYears(k)` for `YEAR`, for k = 0, 1, 2, …. Always compute from `firstBillingOn`; never as `billing(k-1).plusMonths(1)`. `java.time` already moves a missing day back to the month's last day: Jan 31 gives Feb 28 then Mar 31, and Jan 30 gives Feb 28 then Mar 30.
- **R3 — Which billing dates count.** `billing(k)` counts only if `endsOn` is null or `billing(k)` is before `endsOn`.
- **R4 — Current period.** If `D < firstBillingOn`, the period is `[startDate, firstBillingOn)`. Otherwise it is `[billing(k), billing(k+1))` for the largest k with `billing(k) ≤ D`. The end date is exclusive. When the status is `CANCELED`, both period fields are null.
- **R5 — Next billing date.** The earliest counting `billing(k)` that is after `D`, or null if there is none.
- **R6 — Status.** `CANCELED` if `endsOn` is set and `D ≥ endsOn`. Otherwise `TRIALING` if `D < firstBillingOn`. Otherwise `ACTIVE`. Separately, `cancelAtPeriodEnd = endsOn != null && D < endsOn`.
- **R7 — Cancel.** Evaluated with `D` = today:
  - Already `CANCELED`: `IMMEDIATE` returns `200` and changes nothing; `AT_PERIOD_END` returns `409 ALREADY_CANCELED`.
  - `cancelAtPeriodEnd` is true: `AT_PERIOD_END` returns `200` and changes nothing; `IMMEDIATE` sets `endsOn = today`.
  - Otherwise: `AT_PERIOD_END` sets `endsOn` to the current period's end (R4); `IMMEDIATE` sets `endsOn = today`.
  - Whenever `endsOn` changes, `cancelMode` and `canceledOn` are set to the mode and today.
- **R8 — One live subscription.** A subscribe is rejected if the same client has a subscription with the same `customerId` and `planId` whose status today is not `CANCELED`.

**Worked example.** Plan: `MONTH`, 7-day trial. Subscription starts 2026-01-24, so `firstBillingOn` is 2026-01-31. On 2026-03-05 it is canceled with `AT_PERIOD_END`, so `endsOn` becomes 2026-03-31.

| `D` | Status | Current period | `nextBillingOn` | `cancelAtPeriodEnd` |
| --- | --- | --- | --- | --- |
| 2026-01-24 | `TRIALING` | 01-24 to 01-31 | 2026-01-31 | false |
| 2026-01-31 | `ACTIVE` | 01-31 to 02-28 | 2026-02-28 | false |
| 2026-03-05, before the cancel | `ACTIVE` | 02-28 to 03-31 | 2026-03-31 | false |
| 2026-03-30 | `ACTIVE` | 02-28 to 03-31 | null | true |
| 2026-03-31 | `CANCELED` | null | null | false |

## 5. Endpoints

**Check order.** Every endpoint runs its checks in this order and returns the first failure: `401` (key), `400 MALFORMED_REQUEST` (body), `400 VALIDATION_ERROR` (fields, in the order listed), `404` (referenced IDs), then `409` (state).

**SubscriptionView.** Endpoints 2, 3 and 4 all return this object, computed for a date `D` under section 4. (`proposal.md` shows shortened versions.)

```json
{ "subscriptionId": "sub_9f2k1m0xqa", "planId": "pln_3k8d0a2zpr", "customerId": "cus_42",
  "startDate": "2026-01-24", "firstBillingOn": "2026-01-31",
  "status": "ACTIVE", "currentPeriodStart": "2026-02-28", "currentPeriodEnd": "2026-03-31",
  "nextBillingOn": "2026-03-31", "endsOn": null, "cancelAtPeriodEnd": false }
```

### 5.1 `POST /plans`

**Body:** `name`, `priceCents`, `currency`, `interval`, `trialDays`, all required, with the constraints in section 3.

```json
{ "name": "Pro monthly", "priceCents": 999, "currency": "USD", "interval": "MONTH", "trialDays": 7 }
```

**Behavior:** stores the plan.

**Response:** `201` with the stored plan, including `planId`.

**Errors:** `400 VALIDATION_ERROR`; `409 PLAN_NAME_TAKEN` (the name is used by another of this client's plans, ignoring case); `409 IDEMPOTENCY_MISMATCH`.

### 5.2 `POST /subscriptions`

**Body:** `planId` (required), `customerId` (required), `startDate` (optional; default today; must not be after today).

```json
{ "planId": "pln_3k8d0a2zpr", "customerId": "cus_42", "startDate": "2026-01-24" }
```

**Behavior:** applies R8, sets `firstBillingOn` (R1), and stores the subscription.

**Response:** `201` with the SubscriptionView for `D` = today.

**Errors:** `400 VALIDATION_ERROR`; `404 PLAN_NOT_FOUND`; `409 ALREADY_SUBSCRIBED` (the body also carries `existingSubscriptionId`); `409 IDEMPOTENCY_MISMATCH`.

### 5.3 `GET /subscriptions/{subscriptionId}?asOf=YYYY-MM-DD`

**Query:** `asOf` is optional (default today) and must not be before the subscription's `startDate`. It may be in the future, which lets clients ask about a later day.

**Behavior:** read-only.

**Response:** `200` with the SubscriptionView for `D` = `asOf`.

**Errors:** `400 VALIDATION_ERROR` (unparseable `asOf`, or before `startDate`); `404 SUBSCRIPTION_NOT_FOUND`.

### 5.4 `POST /subscriptions/{subscriptionId}/cancel`

**Body:** `mode`, required: `AT_PERIOD_END` or `IMMEDIATE`.

```json
{ "mode": "AT_PERIOD_END" }
```

**Behavior:** applies R7. There is no `Idempotency-Key` here: R7 already makes a repeat of the same mode safe.

**Response:** `200` with the SubscriptionView for `D` = today.

**Errors:** `400 VALIDATION_ERROR` (missing or unknown `mode`); `404 SUBSCRIPTION_NOT_FOUND`; `409 ALREADY_CANCELED`.

### 5.5 `GET /billing-dates?from=YYYY-MM-DD&to=YYYY-MM-DD&customerId=`

**Query:** `from` and `to` are required, with `to` on or after `from` and at most 92 days counting both ends. `customerId` is optional.

**Behavior:** for every subscription of this client (filtered by `customerId` if given), lists each counting billing date (R2, R3) from `from` to `to`, both included. Sorted by `date`, then `subscriptionId`. Dates before today are included; this is a schedule, not a record of charges.

**Response:** `200`. For the worked example with no cancel, from 2026-02-01 to 2026-03-31:

```json
{ "from": "2026-02-01", "to": "2026-03-31",
  "charges": [
    { "date": "2026-02-28", "subscriptionId": "sub_9f2k1m0xqa", "customerId": "cus_42",
      "planId": "pln_3k8d0a2zpr", "amountCents": 999, "currency": "USD" },
    { "date": "2026-03-31", "subscriptionId": "sub_9f2k1m0xqa", "customerId": "cus_42",
      "planId": "pln_3k8d0a2zpr", "amountCents": 999, "currency": "USD" } ] }
```

An empty window returns `"charges": []`, not `404`.

**Errors:** `400 VALIDATION_ERROR` (missing or unparseable dates, `to` before `from`, more than 92 days).

## 6. Error codes

This is the complete list. The service returns no other codes, and no response body ever contains a stack trace.

| Code | Status | Returned when |
| --- | --- | --- |
| `UNAUTHENTICATED` | 401 | `X-Client-Key` is missing or blank |
| `MALFORMED_REQUEST` | 400 | The body is missing or isn't valid JSON |
| `VALIDATION_ERROR` | 400 | A field or query parameter breaks a constraint; `field` names it |
| `PLAN_NOT_FOUND` | 404 | `planId` doesn't exist for this client |
| `SUBSCRIPTION_NOT_FOUND` | 404 | `subscriptionId` doesn't exist for this client |
| `NOT_FOUND` | 404 | The path matches no endpoint |
| `PLAN_NAME_TAKEN` | 409 | Another plan of this client has the same name, ignoring case |
| `ALREADY_SUBSCRIBED` | 409 | R8 blocks the subscribe |
| `ALREADY_CANCELED` | 409 | `AT_PERIOD_END` on a `CANCELED` subscription (R7) |
| `IDEMPOTENCY_MISMATCH` | 409 | A reused `Idempotency-Key` arrives with a different body |
| `INTERNAL_ERROR` | 500 | Anything unexpected; the message is generic |

## 7. Acceptance tests

Each test starts from an empty service with the clock fixed at 2026-03-05 unless it says otherwise. Plan **M7** is `MONTH`, 999 USD, 7-day trial; **M0** is the same with no trial; **Y0** is `YEAR` with no trial. The implementation is done when every test passes under `./mvnw verify`.

| ID | Given | When | Then | Rule |
| --- | --- | --- | --- | --- |
| AT-1 | M0, subscription starting 2026-01-31 | `GET /billing-dates` from 02-01 to 04-30 | Dates 02-28, 03-31, 04-30 | R2 |
| AT-2 | M0, subscription starting 2026-01-30 | `GET /billing-dates` from 02-01 to 03-31 | Dates 02-28, 03-30 | R2 |
| AT-3 | Clock 2032-03-01; Y0, subscription starting 2028-02-29 | `GET /subscriptions/{id}` with `asOf` 2029-03-01, then 2032-03-01 | Period starts 2029-02-28, then 2032-02-29 | R2, R4 |
| AT-4 | M7, subscription starting 2026-01-24 | `GET` with `asOf` 01-30, then 01-31 | `TRIALING`, then `ACTIVE` with `nextBillingOn` 02-28 | R1, R5, R6 |
| AT-5 | AT-4's subscription | Cancel `AT_PERIOD_END` | `200`, `endsOn` 03-31, `cancelAtPeriodEnd` true; `asOf` 03-31 gives `CANCELED`; billing dates 03-01 to 03-31 are empty | R3, R6, R7 |
| AT-6 | Clock 2026-01-26; AT-4's subscription | Cancel `AT_PERIOD_END` | `endsOn` 01-31; billing dates 01-01 to 03-31 are empty | R3, R7 |
| AT-7 | AT-4's subscription | Cancel `IMMEDIATE` twice | Both `200`, `CANCELED`, `endsOn` 03-05 | R7 |
| AT-8 | AT-7's end state | Cancel `AT_PERIOD_END` | `409 ALREADY_CANCELED` | R7 |
| AT-9 | AT-5's end state, then clock 03-10 | Cancel `IMMEDIATE` | `endsOn` 03-10, `CANCELED` | R7 |
| AT-10 | M7, subscription for `cus_42` | Subscribe `cus_42` to M7 again | `409 ALREADY_SUBSCRIBED` with `existingSubscriptionId`; after an `IMMEDIATE` cancel, the same request gives `201` | R8 |
| AT-11 | M7 | Subscribe twice with the same `Idempotency-Key` and body; then reuse the key with another `customerId` | Identical `201` bodies and one stored subscription; then `409 IDEMPOTENCY_MISMATCH` | Section 2 |
| AT-12 | Ten threads | Subscribe at once with the same `Idempotency-Key` | One stored subscription; all ten get the same `subscriptionId` | Section 2 |
| AT-13 | Client A's subscription | Client B calls `GET /subscriptions/{id}` and `GET /billing-dates` | `404 SUBSCRIPTION_NOT_FOUND`; B's charges are empty | Section 2 |
| AT-14 | — | `GET /billing-dates` from 03-01 to 06-01, then from 03-01 to 05-31 | `400 VALIDATION_ERROR` with `field` `to` (93 days); then `200` (92 days) | 5.5 |
| AT-15 | M7 | Subscribe with `startDate` 2026-03-06 | `400 VALIDATION_ERROR` with `field` `startDate` | 5.2 |
| AT-16 | — | Any request without `X-Client-Key` | `401 UNAUTHENTICATED` | Section 2 |
